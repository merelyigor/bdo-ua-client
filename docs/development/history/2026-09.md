## 2026-09-03 · T3 - Background polling cadence

### Problem

Фіксований ~15s API-полер означав, що приховані/background клієнти також опитували API кожні ~15 секунд. Поточна затримка не могла бути скинута при переході режиму; не існувало спільного негайного poll для restore / Check now; негайне опитування мало зберігати одноразову серіалізацію запитів та семантику паузи операції; фінальний concurrency-рев'ю виявив витік власності linked scheduler-wait CTS у першій реалізації.

### Decision

- Збережено один `ReleaseFeedPoller.RunLoopAsync`; додано `ReleaseFeedPollingMode.Visible / Background`; виробничі інтервали 15s / 5min; стан планувальника захищено `_schedulerLock`.
- Скасовний поточний scheduler-wait через `_schedulerWaitCts`; додано `SetPollingMode`, `RequestImmediatePoll`; `PerformPollAsync` — єдиний recurring/immediate шлях API-запиту (`_apiClient.GetReleasesAsync`).
- Зміна режиму скидає поточну затримку без власного poll; restore = Visible + негайний poll; Check now використовує негайний poll без restore.
- Кілька негайних коалесують; активний запит задовольняє суміжний негайний (Option A); Pause авторитетний; Resume запускає свіжу каденцію поточного режиму.
- `RunLoopAsync` володіє кожним linked wait CTS і звільняє його у `finally` через `ReleaseSchedulerWait`; `Dispose` не володіє per-wait CTS.

## 2026-09-04 · T4 - Local file-change trigger

### Problem

API-фід реагує лише на семантичну зміну релізу; гра/ланчер може перезаписати `ads\languagedata_en.loc`, поки API-фід не змінився, тому API-полінг сам не виявляє локальну заміну. Постійне SHA-хешування для резидентного tray-клієнта було б марнотратним. Потрібен дешевий метаданний тригер, чий lifecycle переживає приховані операції та тимчасові збої capture, не помилково моніторячи власні транзакційні записи.

### Decision

- Окремий `System.Windows.Forms.Timer` ~5 хв, яким володіє `MainForm.LocalFileMonitor.cs`; `ReleaseFeedPoller` не змінено (T3 ізольовано).
- Відбиток `LocalizationFileFingerprint`: `Exists` / `Length` / `LastWriteTimeUtc`; відсутній файл — канонічний валідний відбиток; IO-помилки capture тимчасові й ретраяться без просування baseline.
- `LocalFileChangeTracker` — лише RAM, зі зіставленням шляху `OrdinalIgnoreCase`; baseline = відбиток, пов'язаний з останнім успішним `RefreshStateAsync`.
- `RefreshStateAsync` захоплює відбиток ДО `ResolveAsync` і комітить його (лише для валідного API-managed стану) після повної успішної презентації; без пост-резолюційного перезахоплення (інваріант F0/F1/F2).
- Незмінений відбиток → без `RefreshStateAsync`/SHA; змінений/відсутній baseline → існуючий шлях `RefreshStateAsync` (без тихого `CommitResolved(current)`).
- `FeedApplicationCoordinator` серіалізує локальну й API-реконсиляцію: `BlockUpdates()` до першого await, `await RefreshStateAsync()`, `await ApplyPendingIfAnyAsync()`, `UnblockUpdates()` у `finally`.
- Restore виконує одне дешеве порівняння через `BeginInvoke` + `RunLocalFileCheckSafeAsync`; `RestoreFromTray` лишається синхронним.
- Таймер може лишатися живим під час прихованої операції, але фактичний checker повертає до зчитування файлу, доки `_operationInProgress`/`IsBlocked`. Перехід у Official/Missing/Invalid/видимий стан зупиняє таймер із збереженням baseline. Реальне завершення → `DisposeLocalFileMonitor()`.

Корекції під час review:

1. початкова реалізація могла залишити монітор зупиненим після прихованих операцій;
2. початкова реалізація не ретраяла, коли baseline не було встановлено;
3. виправлено розділенням таймер-START/liveness від CHECK-безпеки (operation/feed-blocked більше не є умовою зупинки таймера);
4. фінальний review виявив, що таймер лишався увімкненим після API→Official/Missing/Invalid;
5. виправлено перетворенням `StartLocalFileMonitorIfEligible()` на ідемпотентний синхронізатор eligibility (негативна eligibility зупиняє таймер, зберігаючи baseline).

## 2026-09-04 · T5 - Notifications / dedup

### Problem

- Background client could detect an update without informing the user.
- Repeated polling could spam notifications.
- Notification failure must not break feed/state correctness.

### Decision

- `UpdateAvailable`-only actionability with a RAM-only episode latch.
- Visible observations latch without a balloon; the first hidden episode notifies.
- Non-actionable factual state resets the episode.
- No PublicId/mode dedup, persistence, scheduler, or dependency.
- Generic balloon text; click reuses `RestoreFromTray()`; `ShowBalloonTip` is isolated.

### Changed

- Runtime, pure tests, plans, registry, CURRENT, journal, and §39 repository rules.

### Validation

- Release build: 0 warnings / 0 errors.
- 891 tests passed / 0 failed.
- Static notification integration checks passed.

### Consequences

- Background users can be informed without repeated notifications for one unresolved episode.
- A process restart may notify once again.
- Real Windows visual/click E2E is deferred to T6; T5 remains pending architect review.

### Follow-up

- Architect T5 review, then T6 Owner E2E / resource validation.

## 2026-09-04 · T5/T6 validation resolution

### Problem and investigation

- Native `NotifyIcon.ShowBalloonTip` appeared with the approved title and body, but genuine activation did not deliver WinForms `BalloonTipClicked` on the current Windows notification surface.
- The event was not delivered; `RestoreFromTray()` was never entered. Guards and the MainForm lifecycle were therefore not responsible.

### Decision and change

- The native notification remains informational only; click-to-restore is intentionally outside the first-version contract.
- The unreliable `BalloonTipClicked` subscription was removed. No generic `Click`/`Closed` workaround, Windows App SDK, COM activation, or new dependency was introduced.
- Tray `Відкрити`, tray double-click, and secondary-instance activation remain the canonical restore paths.

### Validation

- T6 Windows UI: X → tray, Open, double-click, Exit, secondary instance, notification appearance, and notification dedup passed.
- Headless background startup, duplicate background instance, approximately 300.7-second cadence, resource sanity, T4 monitor behavior, and process cleanup passed.
- Release build: 0 warnings / 0 errors; 891 tests passed / 0 failed; diff check passed.

### Consequence and follow-up

- T5 and T6 are COMPLETED / REVIEWED / ACCEPTED. The tray/background feature is ready for release preparation.
- A richer actionable Windows toast may be considered separately in the future; it is not part of the current plan.
