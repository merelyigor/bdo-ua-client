## 2026-08-27 · Managed localization overwrite state hotfix

### Problem
When Black Desert or its launcher replaces `languagedata_en.loc` after BDO-UA Client installed a managed localization, and the game patch did not advance (same `ads_files` patch number), the hash mismatch was classified as `Corrupted`. Production v1.1.2 reproduced: install → game/launcher replaces file → same patch → "Файл локалізації пошкоджено".

### Decision
Existing installation metadata (valid API source, known SHA, file exists but different) proves the managed localization is no longer active — regardless of whether a game patch occurred. Classify this recoverably as `UpdateAvailable` (if current release available) or `WaitingForRelease` (if not), using a new `LocalizationPatchTransition.ManagedFileChanged` value. Higher-patch detection (`GameFileReplacedAfterPatch`) preserved unchanged.

### Changed
- `Services/LocalizationStateResult.cs` — added `ManagedFileChanged` enum value + `WithManagedFileChanged` factory

- `Services/LocalizationStatePresentation.cs` — added "Встановлена локалізація більше не активна" headline
- Tests: updated 3 existing expectations, added 5 new test cases (same-patch mismatch, no-patch mismatch, same PublicId after change, null current after change, presentation)

### Validation

## T1.1 - Autostart / background startup (2026-08-29)

### Problem
Застосунок потребував опціонального per-user автозапуску Windows безпосередньо в область сповіщень (background). Оскільки T1.1 робить прихований `--background` клієнт рутинно резидентним, існуюча можливість запуску кількох незалежних нормальних інстанцій стала матеріально небезпечною: дві інстанції могли б одночасно змінювати спільний стан установки, метадані та, потенційно, файли гри.

### Decision
- Per-user автозапуск через `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, значення `BDO-UA-Client` = `"<current-absolute-exe-path>" --background`; без UAC/HKLM/Scheduled Task/Service/Startup-folder, без зовнішніх залежностей. Реєстр — джерело істини; конфіг зберігає лише UX-стан підказки.
- Точний флаг `--background`: Normal startup, але одразу приховано в трей, через той самий `MainForm`/`MainForm_Shown` pipeline; без `ApplicationContext`, без другого процесу.
- Одноразова opt-in підказка після ручного idle X → трей; `Так` увімкнює реєстр і помічає dismissal лише при успіху, `Ні` лише зберігає dismissal; не показується при `--background` та під час активної операції; явний вибір у меню трея також приховує майбутню підказку.
- Меню трея: `Відкрити` → `Запускати разом із Windows` (checkbox з реального реєстру) → separator → `Вихід` (без `Перевірити зараз`).
- Single-instance безпека для нормальних клієнтів: іменований Mutex `Local\BDO-UA-Client.SingleInstance` (власність primary) + AutoReset `EventWaitHandle` `Local\BDO-UA-Client.Activate` (сигнал активації). Manual вторинний запуск сигналізує primary відновитись і завершується; duplicate `--background` завершується тихо; якщо primary немає — свіжий запуск стає primary. Гейт застосовується лише до Normal mode; `--apply-update` його не проходить (helper чекає parent PID, старий процес звільняє Mutex, перезапущений target стає primary).

## T2 - Operation / shutdown semantics (2026-08-29)

### Problem
Два виявлені розриви T2: (1) явний Exit трея під час активної операції запитував скасування, але скидав _explicitExitRequested, тому процес лишався живим і вимагав повторного натискання Вихід; (2) ранній wait _stateService.ResolveAsync(...) у HandleInstallAsync відбувався до створення _operationCts, тому pending shutdown під час ResolveAsync міг продовжитися у нову транзакцію встановлення. Також вимагалася безпечна семантика реального Windows/system закриття під час активної операції.

### Decision
Малий чистий MainFormCloseAction close-policy (HideToTray / ExitNow / DeferUntilOperationCompletes) + поле _exitAfterOperation. Звичайний UserClosing лишається hide-to-tray навіть під час активної операції. Реальне закриття під час активної операції відкладається (e.Cancel = true), _closing = true і _exitAfterOperation = true встановлюються одразу, існуючий CTS-скасування повторно використовується. Після повного безпечного очищення операції CompletePendingExitAfterOperation() планує відкладений BeginInvoke(Close); другий FormClosing обходить hide-to-tray і завершує процес. Без generic lifecycle controller, без ApplicationContext, без hard-kill. Self-update лишається першою спеціальною гілкою FormClosing. Додано guard після ResolveAsync у HandleInstallAsync.
